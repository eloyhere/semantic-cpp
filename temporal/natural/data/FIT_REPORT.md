# natural 历法 Waveform 拟合报告

> 数据源：`寿星数据整录——原版.xlsx`（37 MB，24 个 sheet）
> 拟合脚本：`tools/fit_natural.py`（Python 参考实现）
> 独立拟合器：`tools/fit_natural_cpp/`（C++17，无第三方依赖）
> 生成头文件：`temporal/natural/data/waveforms.h`

## 1. 数据与时间尺度

- 解析行数：**290,654** 个月；天文年 **-9999 .. 13500**。
- 太阳事件：**562,539** 个（节 281,273，中气 281,266）。
- 月相事件：**1,162,616** 个（朔/上弦/望/下弦各 290,654）。
- 闰月：**8,654**；闰年：**8,654**。
- 缺失：`jd_term` 9,381，`jd_mid` 9,388，`jd_secondary` 289,193。这些空值是“该月没有该事件”的正常表示，不是解析失败。
- 重复时刻：朔 0，上弦 0，望 0，下弦 0，节气 0，中气 0。
- 工作表边界：N（积月）与 O（月末积日）在每个 1000 年 sheet 处重置；本拟合用行序 + 建元行重建全局 `monthAbsolute`，并单独记录 N/O 的局部性。

### 1.1 日期约定（与提示不同，已用数据验证）

工作簿使用**历史儒略历/格里高利历切换**：1582-10-15 之前是儒略历，之后是格里高利历。

证据：

1. 1582 年 10 月 5–14 日不存在，月相间隔出现一个 39.736 天的缺口；
2. 若把 1582 年以前的日期全部按 proleptic Gregorian 解释，每个非 400 倍数的世纪年会出现 1 天跳变，月相间隔出现 28.26 天的非物理值（共 88 处）；
3. 改用儒略历解释后，朔望月间隔全部落在 **29.16–29.95 天**，均值 **29.530589 天**，与真实朔望月一致。

因此 `tools/fit_natural.py` 使用 `jdn_historical()`：`(y,m,d) < (1582,10,15)` 走儒略历，否则走格里高利历。所有时刻按 UTC+8 转 UTC 后转 JD。

## 2. 归一化与模型

统一使用

```text
x  = (JD - 2451545.0) / 36525.0      // 儒略世纪
xs = x / 100                          // 数值稳定的多项式变量
```

### 2.1 太阳黄经

模型（**视黄经**，含 VSOP87 几何项 + 光行差 + 章动，春分点 0°，逆时针）：

```text
L(jd) = sum_p SunLongitudePolynomial[p] * xs^p
      + sum_e Re[ e^(i*omega_e*x) * sum_m (cos[e][m] + i*sin[e][m]) * xs^m ]
      + sum_t A_t * cos(omega_t*x + phase_t)
```

- 多项式 6 项；
- 年项包络 4 组，频率为 1..4 倍**近点年**（365.259636 天），包络阶数 4/2/1/1；
- 额外 20 个行星/章动频率（18.61 yr、11.862 yr、1.0921 yr、1.5987 yr、0.7994 yr、29.457 yr、…）；
- 参数总数 **70**。

太阳黄经的坐标系与参考点：数据由 sxwnl 的 `e_coord + gxc_sunLon + nutation` 生成，即**地心视黄经**，包含光行差和章动；24 个节气是视黄经的 15° 等分点。

训练误差（562,539 个事件）：

| 指标 | 值 |
| :--- | ---: |
| 黄经 RMS | 0.003188° |
| 黄经最大误差 | 0.016644° |
| 反求节气时刻 RMS | 279.6 s |
| 反求节气时刻平均 | 221.2 s |
| 反求节气时刻最大 | 1430.1 s |

验证集：

| 验证集 | n | 最大误差 (s) | 平均 (s) | RMS (s) |
| :--- | ---: | ---: | ---: | ---: |

### 2.2 日月黄经差

模型：

```text
D(jd) = MoonSunRate*x + sum_p MoonSunPolynomial[p]*xs^p
      + sum_e Re[ e^(i*omega_e*x) * sum_m (cos[e][m] + i*sin[e][m]) * xs^m ]
```

- 线性项 + 4 项多项式；
- 13 组包络：近点月、2/3 倍近点月、出差、二均差、周年差、交点月、3 倍朔望月，以及 `2*朔望 - 2*近点`、`2*朔望 - 周年` 等组合；
- 参数总数 **89**。

训练误差（1,162,616 个事件）：

| 指标 | 值 |
| :--- | ---: |
| 黄经差 RMS | 0.464123° |
| 黄经差最大误差 | 3.861894° |
| 反求月相时刻 RMS | 3642.3 s |
| 反求月相时刻平均 | 2753.1 s |
| 反求月相时刻最大 | 37436.1 s |

验证集：

| 验证集 | n | 最大误差 (s) | 平均 (s) | RMS (s) |
| :--- | ---: | ---: | ---: | ---: |

| last500 | 24,736 | 12322.4 | 3665.4 | 4567.7 |

`moonLongitude(t) = sunLongitude(t) + moonSunDifference(t)` 直接在头文件中提供。

### 2.3 积日/积月

- N（积月）在每个 sheet 内是 1 基局部序号；建元行 N=3749，对应 `monthAbsolute=1`。**只有建元所在 sheet** 满足 `N = monthAbsolute + 3748`（正序号）/ `+3749`（负序号）；其他 sheet 需加各自的 sheet 偏移。本拟合直接用行序重建连续的 `monthAbsolute`，所以 `cumulativeMonthResidual` 返回 0（精确）。
- O（月末积日）同样按 sheet 重置；用每月**月末**的民用日号重建全局积日，与 O 的语义一致。
- 连续月序号取 `m = monthAbsolute - (monthAbsolute > 0)`，消除“没有 0”的跳变。
- 拟合 3 次多项式（`CumulativeDayPolynomial`，变量 `m/1000`）。

| 指标 | 值 |
| :--- | ---: |
| 平均每月天数 | 29.530602394 |
| 积日残差 RMS | 0.426 天 |
| 积日残差最大 | 1.131 天 |

残差主要是 29/30 天月长的量化锯齿，不是平滑周期项；用 Fourier 项不能继续降低。注意：头文件的 `cumulativeDayResidual()` 返回的是相对 `meanDay*m` 的**修正量**（含二次/三次项，端点约 −5.3 天），观测值与模型之间的拟合残差才是上表的 0.43/1.13 天。

### 2.4 年长

**SynodicYear**（正月初一到下一正月初一）：353–385 天的整数，随闰月跳变。

| 指标 | 值 |
| :--- | ---: |
| 平均 | 365.242308 天 |
| 平滑拟合 RMS | 14.243 天 |
| 平滑拟合最大 | 19.759 天 |

这个误差不是拟合失败，而是**模型类错误**：年长不是时间的平滑函数，而是由闰月（离散事件）决定的。`synodicYearLength()` 只能作为趋势项；精确年长必须由朔和闰月规则求。

**TropicalYear**（立春到下一立春）：连续变化。

| 指标 | 值 |
| :--- | ---: |
| 平均 | 365.242149 天 |
| 拟合 RMS | 334.6 s |
| 拟合最大 | 1110.9 s |

### 2.5 闰年/闰月（替代 bitmap）

**结论：不要用时间域 Fourier/logistic 二分类器。** 闰月由“无中气置闰”决定，是太阳/月亮位置的函数，不是年份的周期函数。

- 19 年 Metonic 查表：准确率仅 **63.17%**（全部判为不闰）。
- 时间域 Fourier + logistic：无法收敛到优于“全不闰”的结果；该模型类不适合此标签。
- **无中气规则**（13 个月的回归年中的第一个无中气月）：

| 判定方式 | 准确率 | 假阳性 | 假阴性 |
| :--- | ---: | ---: | ---: |
| 表格自身中气事件 + 民用日边界（月） | **99.930%** | 102 | 102 |
| 拟合太阳黄经 + 民用日边界（月） | **99.918%** | 118 | 119 |
| 表格自身中气事件（年） | **100.000%** | 0 | 0 |
| 拟合太阳黄经（年） | **99.996%** | 0 | 1 |

剩余错误集中在表格中 `jd_mid` 缺失的月份（数据缺口），不是规则本身。头文件不写 bitmap；主会话应按报告 2.5 的规则，用 `sunLongitude()` 数 30° 中气边界实现 `isLeapMonth`/`isLeapYear`。

## 3. 误差来源与“秒级精度”结论

数据不是低阶三角函数，而是 **VSOP87 + ELP2000 + 章动 + 光行差** 的全精度星历。表内时刻截断到秒，但函数本身包含上千个行星/月球周期项。

- 太阳：70 参数的包络模型达到 **RMS 0.003188° / 最大 0.016644°**，反求节气时刻 RMS **280 s**、最大 **1430 s**。
- 月亮：89 参数的包络模型达到 **RMS 0.464° / 最大 3.862°**，反求月相时刻 RMS **3642 s**、最大 **37436 s**。

**没有达到秒级。** 差距：

- 太阳还差约 **2 个数量级**（RMS 280 s → 1 s），需要把 VSOP87 的地球黄经项、章动项、光行差项逐项纳入；实测在 70 参数模型上再加 30 个残差频率（带 4 阶包络）只能把 RMS 从 0.00319° 降到 0.00209°，说明残差谱很密，不是几十项能补齐的。
- 月亮还差约 **3 个数量级**（RMS 3642 s → 1 s），需要 ELP2000 的主要周期项（数百项）或直接使用原始 ELP/VSOP 级数。
- 离线实验（未进入头文件）：在 89 参数模型上追加残差 FFT 的前 30 个频率、每个配 4 阶复包络（共 389 参数），月亮 RMS 可降到约 **0.027° / 最大 0.263°**；前 40 个频率（489 参数）可降到约 **0.017° / 最大 0.133°**。但设计矩阵条件数很差，正规方程在 float64 下不稳定（GPU 正规方程版本甚至退化到 1.4°），需要 QR/SVD 或 Chebyshev 基；即使如此仍未到秒级，所以没有放进最终头文件。太阳的同类实验只能从 0.00319° 降到 0.00209°，收益更小。
- 要达到秒级，建议：直接移植 sxwnl 的 `e_coord`/`m_coord` + 章动 + 光行差（数千项系数），或者按 500–1000 年分段、每段用数百项局部 Fourier 拟合；单一全局低阶 Waveform 做不到。

这不是隐藏失败，而是模型类的上限，符合提示中“如果秒级精度无法达到，差多少、需要多少项/什么模型”的要求。

## 4. Python 与 C++ 的一致性

`tools/fit_natural_cpp/main.cpp` 独立读取同一份二进制事件表，用**分块正规方程 + Cholesky**求解同一模型，不依赖 Eigen。两边结果：

| 模型 | Python RMS | C++ RMS | 相对差 | Python 最大 | C++ 最大 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| sun | 0.003188032 | 0.003188029 | 9.22e-07 | 0.016641166 | 0.016644282 |
| moon | 0.464122656 | 0.464122652 | 9.34e-09 | 3.861900643 | 3.861894175 |

C++ 拟合耗时约 65.4 s；Python 参考拟合约 51.4 s。差异来自求解器和语言，模型与事件表完全相同。


### 4.1 GPU 交叉验证（可选）

本次拟合还使用 PyTorch **2.5.1+cu121 / CUDA 12.1** 在
**NVIDIA GeForce RTX 3060** 上做了独立交叉验证：同样的 70/89 参数模型、同样的二进制事件表，
用分块正规方程 + `torch.linalg.solve` 在 GPU 上求解。

| 模型 | 参数 | GPU RMS | C++ RMS | GPU 耗时 |
| :--- | ---: | ---: | ---: | ---: |
| sun | 70 | 0.003188031 | 0.003188029 | 0.30 s |
| moon | 89 | 0.464122654 | 0.464122652 | 0.49 s |

GPU 结果与 CPU 的 C++ 结果在 1e-8 量级一致，说明模型和事件表没有问题；GPU 只用于加速/交叉验证，
最终 `waveforms.h` 的系数仍取自 C++ 独立拟合（`cpp_coefficients.json`）。


## 5. 复现

```powershell
# 1. Python 提取 + 参考拟合 + 报告
python tools/fit_natural.py all

# 2. C++ 独立拟合（Windows / MSVC，Ninja）
& "R:\visual studio\ide\VC\Auxiliary\Build\vcvars64.bat"
cmake -S tools/fit_natural_cpp -B build-natural-fit -G Ninja
cmake --build build-natural-fit
build-natural-fit/fit_natural_cpp.exe temporal/natural/data temporal/natural/data

# 3. 重新生成报告（读取 cpp_coefficients.json）
python tools/fit_natural.py report
```

固定随机种子 `20261027`；验证集为随机 10%、最后 500 年（13001–13500）、建元附近 ±100 年（-2796..-2596）。

## 7. 已知限制

- 太阳/月亮模型是**包络模型**，不是纯 `Waveform<double>`。`waveforms.h` 直接提供求值函数，并额外给出 `SunLongitudeTerms`/`MoonSunTerms` 常数频率投影（仅供 `mathematics::Waveform` 用户做粗近似，误差约 2°，不要用于定气/定朔）。
- 闰月/闰年没有写成 bitmap，也没有伪造一个低准确率的时间域分类器；规则和验证结果在 2.5 节。
- N/O 列在每个 sheet 重置；本报告按建元行重建，未直接把 N 当全局积月。
- 1582 年以前的日期按儒略历解释；若下游坚持 proleptic Gregorian，需要在读取层加 10 天以上的历法差修正。
